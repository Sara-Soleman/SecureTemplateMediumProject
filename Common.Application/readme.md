Common.Application Layer Architecture
Architectural Overview
The Common.Application layer acts as the foundational engine for CQRS, pipeline behaviors, cross-cutting concerns, and domain event management. By centralizing these core concerns, individual modules maintain a clean, decoupled, and highly maintainable codebase.

Key Components & Responsibilities
1. MediatR Pipeline Behaviors
The application layer leverages a robust, ordered pipeline of IPipelineBehavior implementation middleware that intercepts every Command and Query execution:

LoggingPipelineBehaviour: Integrates with Serilog and OpenTelemetry (ActivitySource) to track execution lifecycle, capture durations, output structured logs, and flag slow-running commands.

ValidationPipelineBehaviour: Automatically validates incoming requests using FluentValidation rules prior to handler execution.

CommandMetricsBehavior: Emits OpenTelemetry metrics (System.Diagnostics.Metrics) including counters for attempts, successes, and failures, alongside duration histograms.

ExceptionHandlingPipelineBehavior: Centralizes exception intercepting, translating business exceptions (myApplicationException) and validation failures cleanly into functional domain results (IDomainError).

2. Domain Event Dispatcher (DomainEventDispatcher)
Manages the asynchronous publication of domain events (IDomainEvent) generated by aggregates.

Implements a queue-based processing mechanism (Queue<IDomainEvent>) to safely handle cascading or nested domain events triggered during execution workflows.

3. Automated Dependency Injection (ServiceCollectionExtensions)
The extension method AddApplicationLayer automates the registration of application-level services through assembly scanning:

Pipeline Registration: Registers MediatR and configures behaviors in their precise execution order.

Service Scoping: Registers core infrastructure abstractions like IDomainEventDispatcher and IEmailService.

Scrutor Assembly Scanning: Automatically discovers and registers all FluentValidation validators and IDomainEventHandler<> implementations across target assemblies.

يقدم هذا المستند توثيقاً شاملاً لهيكلية ومكونات طبقة الـ Common.Application المشتركة، والتي تم تصميمها وفق مبادئ العمارة النظيفة (Clean Architecture) ونمط (CQRS) لدعم التطبيقات المؤسسية القابلة للتوسع بأعلى معايير الأمان والمراقبة.

🗂️ هيكلية المجلدات والمكونات الرئيسية
تتوزع مكونات هذه الطبقة في تنظيم هندسي دقيق يغطي كافة الجوانب الوظيفية والعرضية:

1. مجلد الـ Abstractions (التجريدات والواجهات)
CQRS: يضم الواجهات والأنماط الأساسية لتنظيم الأوامر (Commands) والاستعلامات (Queries).

DomainEvents: واجهات أحداث الدومين (IDomainEvent) ومعالجاتها (IDomainEventHandler).

Handlers: التجريدات المخصصة لإدارة تدفق العمليات داخل المعالجات.

Messaging: تنظيم رسائل النظام والاتصال الآمن بين المكونات.

IUnitOfWork.cs: واجهة وحدة العمل لإدارة المعاملات وتنسيق الحفظ في قاعدة البيانات.

2. مجلد الـ Behaviours (سلوكيات المعالجة عبر MediatR Pipeline)
سلسلة من المعالجات الوسيطة التي تعترض كل طلب (Command/Query) بترتيب هندسي صارم:

LoggingPipelineBehaviour.cs: لتسجيل وتتبع دورة حياة الطلبات والعمليات البطيئة عبر Serilog و OpenTelemetry.

ValidationPipelineBehaviour.cs: للتحقق التلقائي من صحة المدخلات باستخدام FluentValidation قبل وصول الطلب للمعالج.

CommandMetricsBehavior.cs: لجمع قياسات الأداء الحية والأرقام (Metrics) كعدادات النجاح، الفشل، وزمن التنفيذ.

ExceptionHandlingPipelineBehavior.cs: معالجة مركزية للاستثناءات وتحويلها بسلاسة إلى نتائج وظيفية نظيفة (Result.Failure).

3. مجلد الـ Email (خدمات البريد الإلكتروني)
EmailService.cs: التنفيذ الفعلي لآلية إرسال البريد الإلكتروني في التطبيق.

Interfaces/IEmailService.cs: الواجهة البرمجية لتجريد خدمة البريد الإلكتروني وفصلها عن التفاصيل التقنية.

4. مجلد الـ Events (الأحداث والناشرات)
Dispatchers/DomainEventDispatcher.cs: مسؤول عن نشر وتوزيع أحداث الدومين عبر صف انتظار آمن (Queue) لضمان معالجة الأحداث المتتابعة (Cascading Events) بدقة فورية.

5. مجلد الـ Observability (المراقبة والقياس المتقدم)
CommandMetrics.cs: تعريف العدادات والمؤشرات الإحصائية المعتمدة على OpenTelemetry.

CommonActivitySource.cs: مصدر الأنشطة الموحد لدعم التتبع الموزع (Distributed Tracing).

6. الإعداد المركزي والتسجيل (ServiceCollectionExtensions.cs)
دالة تمديد مركزية (AddApplicationLayer) تؤتمت عملية حقن التبعيات (DI) بالكامل؛ حيث تسجل MediatR، والـ Behaviors، وخدمات البريد، بالإضافة إلى المسح التلقائي (Assembly Scanning) عبر مكتبة Scrutor لتسجيل جميع الـ Validators والـ Event Handlers دفعة واحدة.


ما هي طبقة Common.Application؟هي "العقل المدبر والمنظم" لتدفق العمليات داخل مشروعك. هي المسؤولة عن ترجمة أوامر المستخدم أو النظام (Commands & Queries) وتنفيذها عبر ترتيب هندسي دقيق، مع إدارة المراقبة، التحقق من البيانات، ومعالجة الأخطاء.   🔍 ماذا تفعل وماذا ترسل/تستقبل؟تُدير خطوط المعالجة (MediatR Pipeline Behaviors):ماذا تفعل؟ تستقبل كل طلب (Command/Query) وتمرره عبر سلسلة من السلوكيات التلقائية بالترتيب:LoggingPipelineBehaviour: تسجل تفاصيل الطلب وتتتبع أداءه عبر Serilog و OpenTelemetry.   ValidationPipelineBehaviour: تفحص المدخلات وتتحقق من صحتها باستخدام FluentValidation قبل السماح بتنفيذ الكود.   CommandMetricsBehavior: تجمع مؤشرات الأداء الحية (Metrics) وزمن التنفيذ.   ExceptionHandlingPipelineBehavior: تلتقط الأخطاء وتتحكم في توجيهها بصيغة استجابة نظيفة.   تُنشر أحداث الدومين الداخلية (DomainEventDispatcher):ماذا تفعل؟ تستقبل أحداث الدومين الناتجة عن الكيانات، وتدير صف انتظار (Queue) لنشرها ومعالجتها داخلياً بدقة متناهية.   تؤتمت تسجيل التبعيات (Scrutor Assembly Scanning):ماذا تفعل؟ تبحث تلقائياً في الـ Assemblies الخاصة بالموديولات عن أي Validator أو Domain Event Handler جديد لتسجيله في النظام فوراً دون الحاجة للكتابة اليدوية.   🌱 هل هي ثابتة أم قابلة للتعديل مستقبلاً مع المشاريع الجديدة؟نعم، مرنة وقابلة للتوسعة:
كلما أردت إضافة سلوك جديد يعترض كل الطلبات (مثل إضافة نظام حماية إضافي، أو تتبع نوع جديد من الـ Metrics)، يمكنك إضافة Pipeline Behavior جديد هنا. كما أن دالة التسجيل المركزي (AddApplicationLayer) مصممة خصيصاً لتتقبل تمرير الـ Assemblies الخاصة بأي موديول جديد تود إضافته مستقبلاً لتفعيله بكفاءة تامة.
